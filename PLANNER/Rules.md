# Pramana Cx Engineering and Agent Rules

## Coding Conventions

- TypeScript variables, functions, and API payload properties use `camelCase`; React components and TypeScript types use `PascalCase`.
- Files use `kebab-case` for route-independent modules and the framework's required route naming for app paths.
- Database tables and columns use `snake_case`; entity vocabulary must match `Schema.md` exactly, including `schedule_tasks`, `schedule_versions`, `resources`, and `schedule_events`.
- API paths use plural nouns for collections, for example `/v1/projects/{projectId}/documents` and `/v1/projects/{id}/schedule/documents`.
- Boolean names begin with `is`, `has`, or `can`; timestamps end with `At` in TypeScript and `_at` in SQL.
- Relationship values use the uppercase names defined in `Schema.md`, such as `PROVES`, `BLOCKS`, `PRECEDES`, and `AFFECTS`.
- Keep route handlers thin: authentication, request parsing, and response mapping only.
- Put business logic in domain services; put Postgres queries (via Drizzle) in repository modules; do not issue database queries directly from React components or route handlers.
- Keep readiness rules in `lib/readiness` as a pure rules module with no model-provider, network, or UI imports.
- The CP-SAT scheduling logic must live in a `lib/scheduling` module (e.g. DAG/critical-path helpers, solver request/response typing, delta-classification predicates) that mirrors `lib/readiness`'s purity rule exactly: zero model-provider, zero network, and zero UI imports. `lib/scheduling` may only shape data going into and coming out of the solver call — the actual HTTP call itself must live outside this module, in the domain service.
- Scheduling business logic (delta detection, re-solve triggering, task/resource acceptance, version persistence, explanation orchestration) lives in a `services/scheduling` domain service, following the same domain-service pattern as the readiness and evidence services; it must not query Postgres directly.
- All Postgres access for schedule tables goes through `repositories/scheduling` (or equivalently named) repository modules; only repository modules issue `schedule_tasks`, `schedule_versions`, `resources`, and `schedule_events` queries.
- The CP-SAT solver microservice must be called only through a dedicated client module (e.g. `services/scheduling/solver-client`) wrapped the same way the storage service wraps object-store access: it is the single call site for the solver's internal HTTP API, and no other module may issue an HTTP request to the solver endpoint directly.
- Keep AI provider adapters behind `ModelProvider`; application code must not call a vendor SDK directly. This applies identically to the Gemini-backed schedule extraction/explainer adapter (`GeminiModelProvider`) as it does to the default-provider evidence adapter — no direct `@google/genai` (or equivalent) SDK calls outside that adapter.
- Keep local object-store access behind a storage service that verifies project scope and content hash, for both evidence documents and schedule source documents (contracts, timelines, POs, approvals).
- UI screens own presentation and user interaction; they must call typed API clients rather than construct raw fetch payloads in multiple components, including the schedule/Gantt/critical-path views.
- Database migrations are ordered, committed, and never rewritten after they reach a shared environment; this applies to the `schedule_tasks`, `schedule_versions`, `resources`, and `schedule_events` migrations exactly as it does to existing tables.
- **Agent-service stack override (scoped):** the Commissioning QA Copilot and Supply Chain Visibility & Risk agent-services use Python/FastAPI + Chroma + Neo4j/NetworkX + direct Gemini SDK per the accepted TRD override — but ONLY within those two agent services. The Node core, the schedule module, and every other module keep the `ModelProvider` rule; no other code may import a Chroma client, a Neo4j driver, or the Gemini SDK directly on the strength of this override.
- The two agent-services are reached only through the Node API front door, over TLS on an internal network, following the same single-call-site client pattern as the solver microservice; no UI component or other backend module may call an agent-service endpoint directly.
- **The three native agents carry no stack override — they run on the committed local stack (Node/TypeScript, `ModelProvider`, Postgres + Drizzle, pgvector, Postgres FTS, local object store, BullMQ/Redis) and must not introduce a parallel stack.** The Specification & Quality Compliance Agent lives in a `services/compliance-check` domain service; its comparison business logic (modality routing, groundedness gating, flag proposal) sits there, its deterministic value/unit/tolerance and presence/absence comparisons live in a pure `lib/compliance` module with the same zero-model-provider/zero-network/zero-UI purity as `lib/readiness`/`lib/scheduling`, and all `requirements`/`findings`/`edges` access goes through the existing repository modules — never direct queries from the service or a route handler.
- The Specification agent's grounding tools (`lookup_standard_clause`, `check_precedent`, `compare_spec_values`) are implemented as discrete, individually-testable modules: `compare_spec_values` is pure deterministic numeric compare in `lib/compliance` (no model-provider import); `lookup_standard_clause` and `check_precedent` are retrieval/repository calls, never LLM inference. The `ModelProvider` may orchestrate these as tool calls but must not substitute its own judgment for their return values.
- The Predictive Schedule Risk Engine lives in a single periodic-poll worker module (e.g. `services/predictive-risk`) driven by the local cron/job trigger — **one poll worker, not a multi-agent system**; its materiality-threshold and dedup logic live in a pure `lib/predictive-risk` module (zero model-provider, zero network, zero UI imports), and it emits only through the existing `POST /v1/projects/{id}/schedule/events` path — it must never write `schedule_tasks`/`schedule_versions` or call the solver client directly.
- The Project Knowledge & RFI Intelligence Agent lives in a `services/knowledge` retrieval service; its mandatory-first deterministic metadata-filter predicate is a pure `lib/knowledge` module applied before any pgvector call, and all typed-graph/timeline reads go through the existing `edges`/`audit_events` repositories — no parallel datastore and no bespoke graph store.
- The three native agents' external procurement/lead-time/workforce/weather-forecast feeds (Predictive engine) and any per-doc-type index wiring (RFI agent) are reached through swappable client modules, the same single-call-site discipline used for the solver and AIS/Open-Meteo clients.

## Patterns to Follow

- The delta-detector must always run and classify an incoming `schedule_event` before any re-solve is triggered; a re-solve must never be invoked unconditionally on every event. If the delta-detector determines the event does not affect the current critical path or downstream dependencies, only the task's status/date is updated and no solver call is made and no new `schedule_version` is created. This applies identically to `predicted_risk_delay` events from the Predictive Schedule Risk Engine.
- Every call to the CP-SAT solver microservice must be issued with an explicit request timeout (default 90 seconds, configurable) and a bounded, backed-off retry count. On timeout or exhausted retries, the call fails into a defined `SOLVE_FAILED` state: the prior `schedule_version` and all task statuses remain completely untouched, no partial or inconsistent schedule version is ever persisted, and the triggering event is marked `SOLVE_FAILED` for manual retry.
- Every `schedule_version` is an immutable snapshot (task dates, critical path, solver status) written once, hash-linked to its predecessor and triggering event; a `schedule_version` row is never updated or deleted in place, only superseded by inserting a new version row.
- The solver microservice call must be idempotent per `(schedule_version_id, event_id)` so that a BullMQ job retry cannot double-apply a re-solve or create duplicate versions for the same trigger.
- A cycle detected in the accepted task dependency DAG must block the solve with an explicit, human-actionable error identifying the offending edge, before any CP-SAT call is made.
- All extraction output (schedule `schedule_task` and `resource` proposals, exactly as with requirement proposals) must be schema-validated before insertion into the database; a record failing schema validation is rejected before it is written, never coerced into a best-effort shape.
- Any extraction field that is missing or ambiguous (duration, dependency, vendor, lead time, resource requirement, deadline type, crew/equipment count) must always be routed to a mandatory `NEEDS_REVIEW` human-review queue; it must never be silently defaulted, guessed, or auto-accepted, regardless of confidence score.
- Only `ACCEPTED` schedule task/resource records are eligible for inclusion in a solver DAG; `NEEDS_REVIEW` or rejected records must never be passed to the solver.
- After every re-solve, the explainer agent runs as a separate job step against the already-persisted before/after diff; explainer failure or timeout must never block, delay, or revert the already-persisted `schedule_version` — it only marks that version's explanation as pending/failed for independent retry.
- Concurrent `schedule_event`s against the same task are serialized; the second event's delta check (and any resulting re-solve) must run against the already-updated state, never against a stale snapshot.
- An event referencing a task absent from the current `schedule_version` must be rejected with an explicit error before any delta check or solve is attempted.
- Acceptance checks for numeric/threshold and boolean/presence criteria in the Commissioning QA Copilot must be implemented as deterministic comparison logic (value/unit/tolerance and presence/absence checks) — never LLM inference. Their results are `proposed_pass`/`proposed_fail`, never a final pass/fail, and the UI must label them "Proposed".
- Narrative/qualitative acceptance criteria must always route to `needs_human_review`; the LLM never auto-determines pass/fail for them, and a post-processing step must force the `needs_human_review` status on every narrative/qualitative step regardless of what the LLM output claims.
- A malformed or schema-invalid LLM checklist draft is rejected with a clear error and routed for retry/human review; it must never be partially rendered or persisted as a valid checklist.
- `TEST_FAILED` events are emitted only on a `proposed_fail` verdict, per the TRD orchestrator event contract; a `needs_human_review` step must never emit `TEST_FAILED`.
- `SHIPMENT_DELAYED` and `SHIPMENT_RECOVERED` events are emitted only on a status CHANGE, deduplicated against each shipment's `last_notified_status` — never on every ~30s poll cycle. Exactly one `SHIPMENT_DELAYED` per transition into at-risk/delayed, exactly one `SHIPMENT_RECOVERED` per return to on-time, zero duplicate emits within an unchanged-status poll window.
- `predicted_risk_delay` events are emitted only on a **material change**, deduplicated by a **task + risk-type** key that the engine persists across poll cycles — never on every poll. A risk crossing the threshold repeatedly with no material change produces no new emit; a self-resolved risk updates its flagged state rather than latching a stale risk. This is the same "state change, not re-assertion" intent that governs the shipment events.
- Every event an agent emits must land as an `audit_events` and/or `schedule_events` record per the TRD mapping (`SHIPMENT_DELAYED` through `POST /v1/projects/{id}/schedule/events` as `schedule_events.event_type = 'shipment_delayed'`, `SHIPMENT_RECOVERED` through the same endpoint as the distinct `schedule_events.event_type = 'shipment_recovered'`, `predicted_risk_delay` through the same endpoint as `schedule_events.event_type = 'predicted_risk_delay'`; `TEST_FAILED` as a `findings` record plus gate `BLOCKED` audit event); no agent event may exist only on the in-process `asyncio` bus (Python agents) or only in the engine's in-memory flagged-risk state (Predictive engine).
- A shipment delay (or a predicted risk) that affects multiple schedule tasks MUST persist as one `schedule_events` row per affected task, with the affected tasks resolved via the shipment's/risk's `AFFECTS` edges; the status-change / task+risk-type dedup rule applies per subject (per shipment transition, per task+risk-type), never per row or per poll.
- Graceful degradation is required in the Supply Chain agent: on Open-Meteo failure or timeout, the deterministic delay factor defaults to `0.0` with an explicit "weather unavailable" reason attached to the ETA — never a blocked or guessed ETA. On AIS unavailability, the position falls back to great-circle interpolation and must be transparently labelled simulated (in the UI and in every downstream consumer's payload), never presented as a live fix.
- Graceful degradation is likewise required in the Predictive Schedule Risk Engine: a signal (procurement/lead-time/workforce/weather-forecast) unavailable during a poll cycle is recorded with an explicit **data-unavailable** state and skipped; the engine must never fabricate a risk, silently drop monitoring, or emit `predicted_risk_delay` from a missing signal.
- The Specification agent must run the groundedness gate before any equivalence/substitution flag is proposed: `lookup_standard_clause`/`check_precedent`/`compare_spec_values` must be invoked first, and an ungrounded claim is downgraded to "no precedent found, needs engineering judgment" — never auto-accepted, auto-rejected, or shown as a flag. When a client spec and a referenced standard conflict, both are surfaced with document hierarchy/date, never one silently chosen.
- The RFI agent must apply its mandatory-first deterministic metadata filter (tenant/project/system/asset/gate/doc_type/date/revision) before any pgvector call; the vector search is scoped to the filtered+routed subset only, never a global query. Any answer claim that cannot be tied back to a `source_region_id` is dropped rather than shown uncited, and a filtered no-match returns an explicit no-results answer with zero uncited claims — never a hallucinated answer from outside scope. Similar-RFI retrieval is scoped to a `doc_type = RFI` index and is project-scoped, never cross-project.

## AI Agent Behaviour Rules

- AI may extract, classify, summarize, suggest mappings, and draft actions only within the current project scope, for the default-provider evidence pipeline, the Gemini schedule pipeline, and all five domain agents.
- AI must include source-region citations and confidence for every requirement, finding, schedule task, resource, compliance flag, or RFI answer claim proposal.
- AI must not approve a requirement, set readiness, close a finding/NCR, approve a waiver, sign a test, or create a gate decision.
- AI must not set, mutate, or override a schedule date, critical path, or feasibility result. The Gemini extraction and explainer agents must never write directly to the `schedule_version` or `scheduled_task`/`schedule_tasks` tables under any circumstance; only the deterministic CP-SAT solver's output, persisted by the `services/scheduling` domain service, may write those tables. This extends identically to the domain agents: neither the Commissioning QA Copilot, the Supply Chain agent, nor the Predictive Schedule Risk Engine may write schedule tables directly — their events enter only through the Node `schedule/events` endpoint and the delta-detector pipeline.
- The Gemini explainer agent's sole output is a human-readable narration of a before/after diff that the solver has already produced and that the domain service has already persisted; it never alters, re-ranks, or supersedes any task date or critical-path entry it is narrating.
- AI must surface `UNKNOWN` (for readiness/evidence) or `NEEDS_REVIEW` (for schedule extraction) when the source is missing, conflicting, illegible, stale, or outside the evaluated schema.
- AI-generated text is labelled as a proposal (or, for schedule explanations, clearly labelled as AI-generated) until a human accepts it or, for explanations, until it is displayed alongside the already-deterministic solver result it describes.
- Every LLM-generated clause citation in the Commissioning QA Copilot must be verified against ingested-corpus metadata post-generation, as a deterministic check; a citation whose clause ID has no matching ingested clause is flagged as a possible hallucination and must never be silently accepted or shown as verified.
- A completed all-steps-passed Commissioning test sets its gate to `PENDING_REVIEW`, never `READY`; only an authorized approver may transition a gate. The Commissioning QA Copilot must never certify, sign a test, close an NCR, grant a waiver, or set a gate to `READY`.
- All delay-factor, ETA, and R/A/G status classification math in the Supply Chain agent must be deterministic threshold logic — never LLM output. ETAs must always be labelled estimates, never guaranteed delivery dates. The agent surfaces risk only: it must never reschedule a task, change a gate status, select a vendor, or modify a PO.
- The Specification & Quality Compliance Agent's LLM must never directly judge conformance. Numeric/threshold, categorical/enum, and boolean/presence checks are deterministic comparisons (auto-flaggable, no LLM verdict); narrative/qualitative comparisons produce an LLM "possible mismatch" **suggestion routed to mandatory human review**, never an auto-flag. A detected deviation only *proposes* a `findings` (NCR) record pending human acceptance, citing the exact requirement clause vs. the exact submittal/PO/drawing line with a confidence score plus an `audit_events` entry; no flag closes or accepts itself, and shop-drawing evaluation is limited to extracted text callouts, never geometry.
- The Predictive Schedule Risk Engine may only *detect* risk (predictive/advisory); its mitigation options are proposals only. It must never reschedule, select, or apply an option, and never alter a date, gate, or PO. The re-solve is executed only by the deterministic CP-SAT solver (given a selected option as a constraint change) or a human, through the existing delta-detector → re-solve pipeline. Its delay/probability estimate and materiality decision are threshold logic against the current critical path, not an authoritative schedule value.
- The Project Knowledge & RFI Intelligence Agent synthesizes answers only from filtered, cited chunks within the mandatory-first metadata-filtered subset; every answer claim must cite `source_region_id`, `document_version`, and content hash, uncitable claims are dropped, and similar-RFI suggestions are advisory only — they cite their source RFI record and never auto-answer or close a query. It never sets readiness, gate, schedule, or finding state.
- AI must not approve compliance, close an NCR, or apply a mitigation on the strength of any of the three native agents' output — every native-agent output is a proposal pending human acceptance or deterministic execution, identical to the two Python agents.
- An implementation agent (human or AI coding assistant) implementing the scheduling module may not add auto-accept logic for low-confidence or ambiguous extraction output without explicit user approval; any such change is out of scope by default and must be flagged, not silently implemented. The same prohibition applies to auto-accepting Commissioning checklist drafts, auto-finalizing `proposed_pass`/`proposed_fail` verdicts, auto-verifying flagged citations, auto-accepting compliance flags, auto-applying a predicted-risk mitigation option, and surfacing an uncited or out-of-scope RFI answer.
- The scheduling solver logic residing in `lib/scheduling` must remain completely free of AI/model-provider imports, network calls, and UI imports, exactly like `lib/readiness`; the same purity rule binds `lib/compliance`, `lib/predictive-risk`, and `lib/knowledge`'s deterministic filter. An implementation agent must not import `ModelProvider`, `GeminiModelProvider`, or any HTTP/fetch client into any of those modules.
- An implementation agent may use the direct Gemini SDK, Chroma, and Neo4j only inside the two Python agent-services' codebases; introducing any of them into the Node core (including the three native agents), or introducing `ModelProvider` bypasses anywhere else on the strength of the agent-stack override, requires explicit user approval.
- Chroma and Neo4j/NetworkX are agent-local working stores only; durable truth lives in the platform's Postgres tables (`evidence`, `findings`, `requirements`, `edges`, `schedule_events`, `audit_events`) and local object-store objects. An implementation agent must not persist any authoritative platform record solely in Chroma or Neo4j, and must not read Chroma/Neo4j as a source of truth for readiness, gate state, findings, or schedule state. The three native agents introduce no such working store — the Predictive engine's flagged-risk state and the RFI agent's per-doc-type indexes must resolve back to `schedule_events`/`edges`/`source_regions`, never stand as authoritative records themselves.
- An implementation agent may add functions and tests within the approved PRD/TRD, but must ask before deleting files, changing accepted ADRs, modifying database migrations, changing auth boundaries, folding schedule/critical-path/compliance/predicted-risk status into the readiness computation, or adding an out-of-scope feature (e.g. multi-mode task scheduling, native write-back to a scheduling tool, ML/statistical duration forecasting beyond the Predictive engine's signal/threshold detection, multi-leg/multi-tier shipment tracking, live port-congestion feeds, route optimization, procurement-alternative modelling, drawing/CAD geometry comparison, multimodal photo analysis, cross-project or full-GraphRAG RFI retrieval, or automated telemetry validation).
- An implementation agent must not use customer documents, credentials, production exports, or unlicensed vendor contracts/timelines as test fixtures without explicit authorization and redaction; use synthetic/dummy scheduling data for development and testing. The same applies to shipment records (synthetic/anonymized only), to compliance submittals/POs/shop-drawings and standards/precedent logs (synthetic, clearly-labelled excerpts only), and to any predictive-risk feed and RFI corpus fixtures.

## Security Rules

- Never hardcode secrets, API keys, tokens, signed URLs, solver microservice endpoints/credentials, or customer content. Use environment bindings and secret management (env/vault) for the solver microservice's internal endpoint and any Gemini API credentials, exactly as for the existing evidence-provider/object-store secrets. This extends to the two Python agent-services' internal endpoints, their direct Gemini SDK keys, the aisstream.io API key, and the Predictive engine's procurement/lead-time/workforce/weather-forecast feed credentials.
- Never commit `.env` files, raw uploads, model prompts containing customer data, generated evidence packs, or schedule/compliance source documents (contracts, timelines, POs, approvals, submittals, shop drawings).
- Enforce tenant and project predicates on every Postgres read/write, including all schedule tables (`schedule_tasks`, `schedule_versions`, `resources`, `schedule_events`) and the compliance/RFI/risk queries, identically to existing tables; verify object ownership before issuing a signed URL for any schedule or compliance source document. The RFI agent's user-facing vector search must apply the tenant/project metadata filter before any pgvector call, so semantic retrieval can never cross a tenant/project boundary.
- The solver microservice must be treated as untrusted network boundary: calls to it require TLS and must be authenticated as internal-network requests only (no public ingress); the payload sent to it must be limited to task IDs, durations, dependencies, capacities, and deadlines — never tenant-identifying data beyond what a given solve requires, since the solver service is stateless and does not itself read Postgres or the object store. The two Python agent-services follow the identical posture: TLS, authenticated internal-network requests only, no public ingress, and no tenant-identifying data beyond what a given operation requires. The Predictive engine's outbound feed calls send no tenant-identifying data beyond the signal query itself.
- Use secure, HTTP-only session cookies; require TOTP for approver actions and re-check authorization at decision time; the same project-scoped RBAC roles (e.g. project scheduler/planner, commissioning engineer, QA/QC lead) must be explicitly scoped to schedule, compliance, risk, and knowledge endpoints rather than inheriting broad access implicitly.
- Sanitize rendered source text and comments to prevent script injection; do not render extracted HTML as trusted markup, including extracted schedule task/resource fields displayed in the Gantt/critical-path views, LLM-generated checklist steps/acceptance criteria rendered in the step-execution UI, shipment/weather fields rendered on the Leaflet map and navigator table, compliance clause/line text and LLM mismatch suggestions rendered in the flag-review UI, predicted-risk mitigation text and live-event signals, and RFI answer/claim text rendered in the knowledge surface.
- Apply rate limits to auth, upload, search, AI, export, schedule, compliance, risk, and knowledge endpoints (including `schedule/documents`, `schedule/baseline`, `schedule/events`, `compliance/documents`, `compliance/checks`, and `knowledge/queries`); return retryable responses without leaking account or project existence.
- Audit role changes, source revisions, requirement reviews, evidence state changes, finding disposition, decisions, and exports in the append-only, hash-chained audit event log. Every `schedule_version` transition (creation, supersession by re-solve, and `SOLVE_FAILED` outcome), and every schedule task/resource review action, must produce its own append-only audit event consistent with the existing `audit_events` hash-chain pattern (`before_hash`, `after_hash`, `event_hash`, `previous_event_hash`) — schedule versioning must be fully reconstructible from the audit chain alone. Commissioning test acceptance/failure, gate `BLOCKED` transitions, agent-emitted shipment delay/recovery events, `predicted_risk_delay` emissions, and compliance-flag proposal/acceptance must produce audit events under the same pattern.
- Do not send proprietary standards, customer content, or unlicensed vendor contract/timeline/PO/approval/submittal content to a model/provider (the default `ModelProvider` or Gemini) unless the project has authorized that processing path; Gemini prompt inputs must be project-scoped, redacted for configured personal data, and excluded from shared/cross-tenant model training, identical to the default-provider evidence-extraction path. This binds the Commissioning agent's direct-Gemini calls, the Specification agent's narrative-mismatch suggestions, and the RFI agent's answer synthesis alike; the native agents call Gemini only through the `ModelProvider` adapter.
- No licensed TIA-942, BICSI, or Uptime Institute content may be ingested into the Commissioning or Specification agents' RAG stores, prompts, embeddings, precedent logs, or demos; only small, clearly-labelled synthetic standard excerpts (and, for compliance, a synthetic approved-equal precedent log) are permitted, structured to be swappable for a licensed corpus later without architectural change.
- AIS (aisstream.io) and weather (Open-Meteo) integrations are free-tier and restricted to non-commercial hackathon use only; production use requires licensed weather and a persistent single-socket AIS feed. Both connectors, and every Predictive-engine external feed, must be abstracted behind swappable client modules, and OpenStreetMap tile usage must carry the required ODbL attribution.
