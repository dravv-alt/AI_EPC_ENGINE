# Architecture Decision Records

## Key Architectural Choices

### ADR-001: Use a local modular monolith for the MVP
**Decision:** Use a Next.js application self-hosted on a local Node.js process (`next start`) with domain modules rather than separate microservices.
**Rationale:** The pilot has a bounded workload, a small engineering team, and a freemium cost constraint (PRD Constraints: "The MVP supports one bounded pilot project..."; PRD Risks: "Free-tier constraints"). The product still needs one consistent authorization boundary across project data, source objects, readiness, and approvals.
**Trade-offs accepted:** Deployment and local reasoning are simpler, but module boundaries must be enforced in code and high-volume modules may later need extraction into separate services.

### ADR-002: Use local Postgres and Drizzle for authoritative relational data
**Decision:** Store normalized authoritative records in a local Postgres database accessed through Drizzle ORM.
**Rationale:** Readiness requires joins across projects, requirements, assets, gates, evidence, findings, and decisions (PRD "Deterministic readiness rules and a red/amber/green board with blocker ownership"). The pilot graph is bounded and must support migrations and database-level foreign keys.
**Trade-offs accepted:** The `edges` table uses application validation for polymorphic endpoints, and complex graph workloads may later require a database migration.

### ADR-003: Store source files and exports in a local object store
**Decision:** Store immutable originals and generated exports in a local object store (MinIO / filesystem-backed), with object keys and hashes in Postgres.
**Rationale:** PRD US-02 requires that "Each accepted upload stores a SHA-256 hash, revision state, uploader, timestamp, and source location," and US-08 requires a hash-manifested evidence-pack export; binary objects should not sit in relational rows or on ephemeral local process filesystems.
**Trade-offs accepted:** Signed URL generation and lifecycle cleanup are required; every export must retain its manifest and source hashes.

### ADR-004: Use hybrid lexical and semantic retrieval
**Decision:** Use Postgres full-text search (tsvector) for exact retrieval and local pgvector for project-scoped semantic retrieval, requiring a source-region citation for every usable result.
**Rationale:** PRD/StructuredPlan scopes lexical search to exact citation/evidence lookup (Postgres full-text search (tsvector) primary for exact identifiers/numeric clauses), while local pgvector provides project-scoped semantic retrieval that is now **user-facing** — powering the RFI Intelligence Agent's scoped, metadata-filtered semantic search ([[ADR-021]]). This supersedes the earlier StructuredPlan Q10 "internal-only" framing for vector search (extraction/classification matching), which was overtaken by the approved PRD's user-facing RFI semantic-search requirement; the boundary with the excluded "broad/global RFI intelligence" is now kept clean by the mandatory-first deterministic metadata filter rather than by hiding vector search internally.
**Trade-offs accepted:** Two indexes must be updated idempotently and retrieval results need project namespace filtering and citation validation.

### ADR-005: Make ingestion durable and asynchronous
**Decision:** Use local BullMQ + Redis for resumable job state and fan-out, with idempotency keys on every processing stage.
**Rationale:** PRD Constraints require durable jobs to be "retryable and idempotent; duplicate delivery cannot duplicate authoritative evidence"; OCR, extraction, indexing, and evidence-pack generation can exceed request limits and depend on unreliable model providers.
**Trade-offs accepted:** Job status, retry limits, dead-letter handling, and user-visible pending states are required.

### ADR-006: Keep readiness deterministic and approvals human-controlled
**Decision:** AI may propose structured records and explanations; a deterministic rules engine alone computes readiness, and an authorized human alone signs decisions.
**Rationale:** PRD Constraints state "Only the deterministic rules engine computes gate readiness; only an authorized human with the configured approval role signs a gate decision," directly to prevent the "False assurance" risk identified in the PRD Risks section.
**Trade-offs accepted:** The product must expose `UNKNOWN` and `BLOCKED`, maintain rule versions, and provide review queues instead of optimizing only for automation.

### ADR-007: Use project-scoped RBAC with strong approval authentication
**Decision:** Use Better Auth sessions, project membership roles, object-level authorization, and TOTP for approver roles.
**Rationale:** PRD US-01 requires that "A user without project membership receives `403`" and "A reviewer cannot perform an approver action"; customer documents and gate decisions require tenant isolation and distinct permissions for viewers, reviewers, field engineers, and approvers.
**Trade-offs accepted:** Every API query must include tenant/project predicates, and role changes must be audit events.

### ADR-008: Make the field experience an offline-capable PWA
**Decision:** Implement the field capture path as a PWA with a local pending queue and explicit sync states.
**Rationale:** PRD Edge Cases require "Offline field captures remain queued locally with a visible sync state and are never shown as accepted until uploaded and processed"; field engineers capture evidence in areas with unreliable connectivity, and the MVP needs a responsive browser workflow without a separate mobile app.
**Trade-offs accepted:** Local storage must be bounded and encrypted where supported; queued evidence cannot become accepted until server processing completes.

### ADR-009: Run CP-SAT as a dedicated solver microservice, not WASM-in-process or a hosted optimization API
**Decision:** Run CP-SAT (Google OR-Tools) inside a small containerized HTTP microservice (Python, official `ortools` package), called from a local BullMQ + Redis job step as a discrete, idempotent, retryable step, with the DAG/capacities/deadlines passed in on each call and no state held by the service.
**Rationale:** PRD US-09/US-10 require a feasible baseline and warm-started re-solve within stated latency budgets (TRD NFR: baseline p95 <= 60s for 500 tasks/50 resource types; re-solve p95 <= 30s), and PRD/TRD require an explicit infeasibility/bottleneck report rather than a silent failure. The schedule module needs a correct, mature constraint solver (Library-First Rule) invoked from a local Node core stack that is otherwise JS/WASM-only.
**Trade-offs accepted:** An additional deployable service and a network hop per solve are required; mitigated by treating each solver call as an idempotent, retryable BullMQ + Redis job step and keeping the service itself stateless and tenant-data-minimal (TRD Security section). Solver-service failures must leave the prior schedule version untouched and mark the event `SOLVE_FAILED` for manual retry (TRD NFR: Solver timeout/fallback).

### ADR-010: Route schedule task/resource extraction through ModelProvider with a mandatory human-review gate for ambiguous fields
**Decision:** Implement schedule extraction/explanation as a second concrete `ModelProvider` adapter (`GeminiModelProvider`), never called directly from schedule services; any missing or ambiguous field is flagged `NEEDS_REVIEW` and routed to a mandatory human review queue (`POST /v1/schedule/tasks/{id}/review`, `POST /v1/schedule/resources/{id}/review`); only `ACCEPTED` records are eligible for solving.
**Rationale:** PRD US-09 and the Constraints section require task and resource-capacity records (duration, dependencies, vendor, lead time, crew/equipment counts) to be extracted without ever silently guessing or auto-accepting an ambiguous or missing field — mirroring the existing requirement-extraction pattern ([[ADR-006]]). TRD specifies Gemini as the schedule-extraction model, distinct from the default local `ModelProvider` evidence adapter used for evidence, and CLAUDE.md's Coding Rules require all AI provider access to go only through `ModelProvider`.
**Trade-offs accepted:** Every schedule extraction job depends on a review-queue UI and reviewer availability before a baseline solve can be triggered; extraction throughput is bounded by human review capacity, which is an accepted trade-off against extraction correctness and auditability.

### ADR-011: Deterministic objective ordering (deadline overrun first, idle time second) as a hard architectural rule, never delegated to the LLM
**Decision:** Encode the two-tier objective (minimize deadline overrun first, then total idle time) as a fixed, code-level parameter of the CP-SAT model itself, never as a value inferred or adjustable by the LLM extraction or explainer agents.
**Rationale:** PRD's Proactive Schedule Management Module section and US-10 specify a deadline-overrun-first, idle-time-second optimization objective (`w1 >> w2`), with an explicit minimum-overrun and bottleneck report when a deadline is infeasible. The PRD's Non-negotiable boundary and the TRD's "Model output cannot mutate ... schedule dates" constraint forbid the LLM from proposing or overriding any schedule date.
**Trade-offs accepted:** Objective tuning requires a code change and redeploy rather than a runtime/config toggle exposed to the LLM or end users; this trades flexibility for auditability and determinism, consistent with the product's AI-advisory-only boundary.

### ADR-012: Immutable, append-only schedule_version history instead of mutable in-place schedule updates
**Decision:** Store every baseline solve and re-solve as a new, immutable `schedule_version` row (task dates, critical path, solver status) linked to its predecessor and triggering `schedule_event`; never update a shared "current schedule" row in place.
**Rationale:** PRD US-10 and US-11 require every re-solve to produce "a new immutable schedule version with full history retained," and TRD's Data Storage section states each `schedule_version` is a complete immutable snapshot with a pointer to its predecessor and triggering event, mirroring the existing "no authoritative readiness value stored as an unversioned mutable flag" rule ([[ADR-006]] lineage).
**Trade-offs accepted:** Storage grows with every re-solve event; this is accepted because auditability (PRD US-11 and the turnover-export requirements) and the explainer agent's before/after diff generation both depend on retaining every historical version untouched.

### ADR-013: Delta-detector gating re-solves, rather than re-solving on every schedule event
**Decision:** Route every `schedule_event` through a delta detector that checks the event against the current `schedule_version`'s critical path and dependency structure; if unaffected, only the task's actual status/date is updated (no new version, no solver call); if affected, a BullMQ + Redis job step calls the solver microservice warm-started from the current version.
**Rationale:** PRD US-10 states an event should trigger a re-solve "only when it actually matters so that the schedule stays accurate without noisy churn," and TRD's NFRs bound baseline/re-solve latency (p95 <= 60s / 30s) — re-solving on every event would multiply solver load and cost without proportional value when an event does not affect the critical path or downstream dependencies.
**Trade-offs accepted:** The delta detector itself becomes a piece of logic that must be correct (a missed impacted-event would leave a stale schedule); concurrent events against the same task are serialized so the second event's delta check runs against already-updated state (TRD Delta Detection and Solve section), and an event referencing a task absent from the current version is explicitly rejected rather than silently ignored.

### ADR-014: Adopt a distinct Python agent-services stack for the Commissioning QA Copilot and Supply Chain agent, reconciled as internal services like the solver microservice
**Decision:** Implement the two newly-integrated agents (Commissioning Quality Assurance Copilot, Supply Chain Visibility & Risk Agent) on a Python/FastAPI + Chroma (RAG) + Neo4j/NetworkX (internal working graph) + direct Gemini SDK + in-process `asyncio` stack — a **distinct local Python stack alongside the platform's local Node/`ModelProvider` stack** for these two agents. Because the whole platform is now local, there is no Cloudflare baseline to diverge from; the two agents are simply a second local stack, reconciled architecturally — not as an exception — using the same pattern already applied to the CP-SAT solver ([[ADR-009]]): they are separate, stateless-with-respect-to-authoritative-state Python services that the local Node core reaches over an authenticated internal-network HTTP API, and whose durable outputs (findings, evidence, report artifacts, `schedule_events`) are written back through the local Node core into Postgres/the local object store/the typed-edges provenance graph under the existing review, audit, and citation rules. The agents' Chroma and Neo4j stores are local working stores only, never the authoritative system of record.
**Rationale:** StructuredPlan's Divergence Note and the two agent committed-design sections, the PRD's "Stack override" constraint, and the TRD's "Agent-services integration approach — accepted" record this as an explicit user decision to let the Python stack stand for these agents as a distinct local stack rather than conforming them to the platform's local Node/`ModelProvider` stack or leaving the choice open. Mirroring the solver-microservice integration keeps the local Node core in its existing JS/TS toolchain while letting each agent use libraries (turfpy, PyMuPDF, ReportLab, `websockets`, Chroma) with no local Node-process equivalent, consistent with the localhost-only hackathon-build assumption (StructuredPlan Q12).
**Trade-offs accepted:** A polyglot backend results, and the TRD explicitly records a hackathon-local-vs-committed split rather than resolving the divergence here: the **direct-Gemini-SDK-outside-`ModelProvider`** call path is *genuinely committed* for these two agents (the schedule module's Gemini use remains behind `GeminiModelProvider`, [[ADR-010]]); whereas **Chroma alongside pgvector**, **Neo4j alongside Postgres**, and the **in-process event bus** are *hackathon-local-only* conveniences whose production reconciliation (consolidate onto pgvector/Postgres/BullMQ, or retain) is deferred to the TRD/pilot stage. The full polyglot reconciliation is not resolved in these planning documents.

### ADR-015: Pin an orchestrator event contract now while leaving the full orchestrator deferred
**Decision:** Define a three-event contract — `TEST_FAILED` (Commissioning agent), `SHIPMENT_DELAYED` and `SHIPMENT_RECOVERED` (Supply Chain agent) — with fixed emit conditions and payloads, and a shared **status-change-only dedup** rule (an event fires only when the newly-computed status differs from the last-notified status, never on every poll cycle). Route these through the existing `POST /v1/projects/{id}/schedule/events` path (a delay lands as `schedule_events.event_type = 'shipment_delayed'`; a recovery lands as the distinct `schedule_events.event_type = 'shipment_recovered'`) into the unchanged delta-detector → CP-SAT re-solve pipeline for the shipment events, and into the evidence-graph pipeline (findings + gate `BLOCKED`) for `TEST_FAILED`. Use an **in-process `asyncio` event bus for the hackathon** and explicitly defer a durable, replayable broker; leave the full orchestrator agent (durable transport, routing rules, replay/ordering) **not-yet-settled**.
**Rationale:** StructuredPlan's Divergence Note ("Orchestrator still emerging") and the TRD's "Orchestrator event contract (emerging design)" pin down only the contract the orchestrator must eventually carry, because the two agent designs newly fix these event types, emit conditions, and dedup semantics while the orchestrator's transport and replay remain undefined. Status-change dedup is required by PRD US-23 and the ~30s AIS poll interval to prevent poll spam into the schedule pipeline; the shipment agent is only a new *producer* of existing event types, so no new downstream solver logic is introduced ([[ADR-013]] lineage). The Predictive Schedule Risk Engine later adds a fourth producer event, `predicted_risk_delay`, under the same status-change/material-change dedup discipline ([[ADR-020]]); the unified "Command Center" alert surface ([[ADR-022]]) reads from the `schedule_events`, `findings`, `edges`, and `audit_events` records the agents already write — no parallel datastore.
**Trade-offs accepted:** The in-process bus gives no durability or replay guarantee, so agent-emitted events reach the durable schedule pipeline only through the local Node core `schedule/events` endpoint (backed by BullMQ/Redis), which remains the production path; a durable/replayable orchestrator transport is a not-yet-settled production requirement rather than a committed design. Defining the contract before the orchestrator means the contract is the stable interface and the orchestrator's routing/replay can be designed later without breaking the two agents.

### ADR-016: Commissioning step-execution UI with "Proposed" verdict badges and a DRAFT—PENDING report review gate
**Decision:** Deliver the Commissioning QA Copilot's execution surface as a step-by-step checklist-execution UI (React 19 + Tailwind + Zustand + TanStack Query), where each executed step's deterministic verdict is displayed as a **"Proposed" `proposed_pass`/`proposed_fail` (or `needs_human_review`) badge**, and auto-drafted test reports are labelled **"DRAFT — PENDING ENGINEER REVIEW"** and gated behind explicit engineer approval before the test record is created as `evidence`, linked to its gate, and added to the turnover pack.
**Rationale:** PRD US-14 requires per-step field-reading capture with resumable persisted state; US-15 requires narrative/qualitative steps to be visibly routed to human review; US-17/US-18 require the draft-review-then-approve-then-link sequence. Labelling every verdict "Proposed" and every report "DRAFT — PENDING ENGINEER REVIEW" directly serves the platform-wide **False assurance** mitigation ([[ADR-006]]): a completed all-pass test sets the gate to `PENDING_REVIEW`, never `READY` — only an authorized approver transitions a gate. The chosen client libraries match the agent's committed stack (TRD Tech Stack row; [[ADR-014]]) and the platform's existing React 19/Tailwind web layer.
**Trade-offs accepted:** Export and evidence linkage cannot happen until an engineer explicitly approves the draft, bounding throughput on reviewer availability — accepted in exchange for keeping AI output advisory and the audit trail human-gated. The step-execution UI must persist and resume partial step state without loss (US-14), adding client/server state-sync complexity over a single-submit form.

### ADR-017: Render shipments on a Leaflet map with a click-to-zoom navigator, great-circle routes, and explicit live-vs-simulated position labelling
**Decision:** Render the Supply Chain agent's shipments, routes, and weather on a **Leaflet/React-Leaflet** map backed by **OpenStreetMap tiles (ODbL, attributed)**, paired with a **click-to-zoom navigator table**; draw routes as **great-circle** paths (turfpy server-side / `@turf` client-side), **split at the antimeridian** so a route crossing ±180° renders as continuous segments rather than a wrong straight line across the map; and label every rendered vessel position transparently as **live (AIS)** or **simulated (great-circle interpolation)**.
**Rationale:** PRD US-19 requires the live-vs-simulated position distinction; US-22 requires the Leaflet map plus a navigator table with click-to-zoom. The TRD Supply Chain flow commits Leaflet/React-Leaflet, OpenStreetMap tiles under ODbL attribution, and `turfpy` great-circle interpolation as the AIS-unavailable fallback. Antimeridian-safe splitting follows directly from rendering great-circle routes on a Leaflet canvas — a single-leg origin→destination path can cross the 180° meridian and must be split to render correctly. The explicit position-source label is the map-side expression of the same "never present a simulated fix as live" rule enforced in the ETA/status engine ([[ADR-018]]). The single-leg (origin→destination) scope means the map draws one route per shipment with no multi-tier/multi-hop legs to render.
**Trade-offs accepted:** OpenStreetMap tiles require visible ODbL attribution and are free-tier/non-commercial (production needs a licensed tile/weather source, per the hackathon-scope note). Antimeridian handling and great-circle rendering add client geometry work versus naive straight-line polylines; accepted because an unsplit great-circle route would display a visibly incorrect path. The single Mumbai demo destination is supported-but-untested for multi-site rendering.

### ADR-018: Confine the LLM to drafting and suggestion; keep all acceptance and shipment classification deterministic
**Decision:** Make the Commissioning acceptance verdicts (numeric/threshold and boolean/presence) and the entire Supply Chain delay/ETA/status computation **deterministic threshold math, never LLM output**. Confine the LLM strictly to: (a) drafting checklists (steps, acceptance criteria, cited clauses) for human review, (b) narrative/qualitative similarity comparison surfaced as a "possible mismatch" *suggestion only*, always routed to `needs_human_review` and never auto-determined, and (c) drafting the test-report narrative. Verify every LLM-generated clause citation against ingested-corpus metadata post-generation; flag hallucinated clause IDs rather than showing them as verified.
**Rationale:** PRD US-15/US-20/US-21 and the Constraints section require that no pass/fail verdict, ETA value, or R/A/G status is produced by the LLM; the TRD's "Commissioning acceptance determinism" and Supply Chain NFRs make this a golden-set-tested requirement. This extends the platform's existing AI-advisory/deterministic-computation boundary ([[ADR-006]], [[ADR-011]]) to the two new agents and mirrors the Specification & Quality Compliance Agent's requirement-modality tiering (deterministic for numeric/categorical/boolean, LLM-suggestion-only for narrative). Post-generation citation verification is a deterministic check, not an LLM self-assessment, preventing hallucinated clause IDs from reaching a reviewer as "verified."
**Trade-offs accepted:** The determinism boundary is drawn per requirement modality, so narrative/qualitative acceptance always requires a human and cannot be auto-cleared, bounding automation on reviewer availability — accepted as the direct cost of keeping every consequential verdict auditable and non-hallucinated. Deterministic ETA/status is a heuristic (an additive delay-factor multiplier), explicitly labelled an estimate rather than a guaranteed date, trading predictive sophistication for explainability and the no-LLM-guess guarantee.

### ADR-019: Specification & Quality Compliance Agent — a proposed-findings review queue with modality-tiered flag states and clause-vs-line evidence diffs
**Decision:** Deliver the Specification & Quality Compliance Agent's frontend as a **compliance flags / review-queue** surface (Next.js/React served locally by the self-hosted Node process, `next start` — no edge delivery), consistent with the existing requirement-review and findings UX. Each row is a **proposed** deviation with a status badge tiered by `requirements.modality`: `deterministic_flag` (numeric/threshold, categorical/enum, boolean/presence — auto-detected, shown with a machine-computed confidence), `possible_mismatch` (narrative/qualitative LLM suggestion, always visibly tagged "AI suggestion — needs human review", never auto-flagged), and `needs_engineering_judgment` (an equivalence/substitution claim that failed groundedness). Every flag opens a **clause-vs-line evidence diff** panel showing the exact accepted-`requirements` clause on one side and the exact submittal/PO/shop-drawing text-callout line on the other, each deep-linking to its `source_region_id`. Equivalence claims render their grounding provenance inline — the retrieved standards clause (`lookup_standard_clause`) or approved-equal precedent (`check_precedent`) that supports them, or an explicit "no precedent found" state when downgraded. A client-spec-vs-standard conflict is presented as a **two-source panel** with document hierarchy/date, never silently resolved. Accepting a flag creates the `findings` (NCR) record (owner, severity, due date) and writes the `audit_events` entry through the local Node core; the UI itself never closes or accepts a flag on the AI's behalf.
**Rationale:** PRD US-24/US-25 and the Agent Suite "UI surface: Flags/review queue" require proposed findings pending human acceptance, exact clause-vs-line citation on every flag, modality-tiered determinism vs. suggestion, and grounded-or-downgraded equivalence handling with conflicting sources surfaced. Presenting narrative comparisons as a distinctly-tagged "AI suggestion" and requiring a human to accept before a `findings` record exists is the frontend expression of the platform's AI-advisory-only boundary ([[ADR-006]], [[ADR-018]]) and the "no flag closes or accepts itself" constraint. Reusing the existing findings/requirement-review React layer (rather than a new surface) matches the agent's design as an extension — not a duplicate — of the requirement-extraction/evidence-graph pipeline (`services/compliance-check` on the existing `ModelProvider`/`requirements`/`edges` infrastructure).
**Trade-offs accepted:** No flag becomes a `findings` record until a human accepts it, so the queue depth is bounded by reviewer availability — accepted as the cost of zero LLM auto-flagging. The clause-vs-line diff and grounding-provenance panels add per-flag rendering and source-region fetch work over a flat list; accepted because a flag with no visible exact-citation evidence would fail the "100% of flags cite an exact clause and an exact line" success metric.

### ADR-020: Predictive Schedule Risk Engine — dedicated "Live Events" and "Delays/Risks" surfaces presenting advisory `predicted_risk_delay` alerts cross-linked to the critical path
**Decision:** Deliver the Predictive Schedule Risk Engine's frontend as **two dedicated tabs** — a **"Live Events"** feed of the real-time polled signals (procurement status, equipment lead times, workforce availability, weather forecast, each with an explicit *data-unavailable* state when a signal feed is missing that poll cycle) and a **"Delays/Risks"** list of flagged **advisory `predicted_risk_delay`** alerts. The engine is a **single locally-run periodic-poll agent** (a self-hosted scheduler/cron process, not a Cloudflare Worker/cron), so the UI presents a poll-driven feed, not a live socket stream. Each risk card shows the affected task(s), estimated delay/probability, source signal, and **one or more mitigation options rendered as proposals only** — selecting an option never reschedules from the UI; it hands the option to a human or, as a constraint change, to the deterministic CP-SAT solver through the existing delta-detector → re-solve pipeline. Every flagged risk **cross-links to the affected task on the schedule/critical-path view** without altering any schedule date, and the flagged-risk state updates (or clears) on material change so a self-resolved risk does not latch stale in the list.
**Rationale:** PRD US-26/US-27 and the Agent Suite "UI surface: dedicated 'Live Events' and 'Delays/Risks' tabs, cross-linked to the schedule/critical-path view" require exactly these two surfaces, mitigation options presented as proposals, and cross-linking that never mutates a schedule date. Rendering mitigation options as non-actionable proposals and keeping the re-solve on the deterministic pipeline is the frontend expression of the engine's "only risk *detection* is predictive/advisory" boundary ([[ADR-006]], [[ADR-011]] lineage) and mirrors how shipment/test events are presented as producers, not deciders. The explicit per-signal data-unavailable state satisfies the edge case that a missing feed is shown, never fabricated. `predicted_risk_delay` is the fourth producer event on the pinned orchestrator contract ([[ADR-015]]) and appears on the Command Center ([[ADR-022]]).
**Trade-offs accepted:** Because the engine is a single periodic-poll agent, the "Live Events" feed refreshes on the poll interval rather than instantly, and a risk can appear up to one interval after its signal changes — accepted as the cost of a simple, deterministic-dedup poll model over a streaming pipeline. Mitigation options are advisory text/structured proposals with no one-click apply, so acting on a risk requires a human decision or an explicit solver re-solve — accepted to keep every schedule-date change on the deterministic solver.

### ADR-021: Project Knowledge & RFI Intelligence Agent — a user-facing semantic-search + cited-answer chatbot and an interactive `edges`-backed project graph/timeline page
**Decision:** Deliver the RFI Intelligence Agent's frontend as **three user-facing surfaces** (Next.js/React served locally by the self-hosted Node process, `next start`; no edge delivery): (a) a **semantic project search** box, (b) a **query chatbot** that returns a natural-language answer in which **every claim is a citation chip** deep-linking to the exact source PDF/doc region and showing `source_region_id`, `document_version`, and content hash — with a distinct **"no results in scope"** answer state (zero uncited claims) when the mandatory-first deterministic metadata filter matches nothing, and a **"previously resolved similar RFI"** suggestion panel (advisory, each citing its source RFI record, never auto-answering or closing the query), and (c) an **interactive project graph/timeline page** whose nodes are entities (event/doc/test/decision) read live via API from the existing append-only, hash-chained `edges` + `audit_events` tables — clicking a node expands its linked docs, vendor supply records, and audits through existing FK relations. No claim renders without a citation chip; uncitable retrieved claims are dropped rather than shown.
**Rationale:** PRD US-28/US-29/US-30 and the Agent Suite "UI surface: Chatbot + interactive project graph/timeline page" require a citation-grounded NL chatbot, project-scoped similar-RFI suggestions, and a live `edges`/`audit_events`-backed graph/timeline with click-to-expand — and the hard constraint requires the user-facing semantic search, the query chatbot, and the interactive graph/timeline to all be reflected as surfaces. Making every claim a citation chip and dropping uncitable claims is the frontend enforcement of the "every answer claim cites `source_region_id`, `document_version`, and content hash; vector search never global" constraint and satisfies the "100% of answer claims cite" success metric. Reading the graph/timeline live from `edges` + `audit_events` (no parallel datastore) keeps the surface consistent with the append-only provenance graph.
**Trade-offs accepted:** Rendering every claim as a source-region-resolving citation chip and driving the graph page live from `edges`/`audit_events` adds per-claim and per-node fetch/hydration work over a plain answer stream or a static diagram; accepted because an uncited claim or a stale parallel-graph node would violate the citation-grounding and single-source-of-truth constraints. Similar-RFI suggestions are advisory-only and project-scoped, so the chatbot cannot reuse a cross-project answer or auto-close a query — accepted per the RFI scoping constraint.

### ADR-022: Command Center — a unified read/cross-link alert surface honoring the full four-event contract with status-change dedup and recovery-clearing
**Decision:** Deliver the Command Center (US-31) as a **single unified alert surface** (Next.js/React served locally by the self-hosted Node process, `next start`; no edge delivery) that reads from the existing `schedule_events`, `findings`, `edges`, and `audit_events` records — no parallel datastore — and cross-links each of the **four** triggering events to its downstream impact: `TEST_FAILED` → the created `findings` (NCR) record and the gate it set to `BLOCKED`; `SHIPMENT_DELAYED` → the affected schedule task(s) and, when a re-solve occurred, the resulting `schedule_version`; `predicted_risk_delay` → the affected task(s) on the schedule/critical-path view and its proposed mitigation options ([[ADR-020]]); and `SHIPMENT_RECOVERED` → the stale `SHIPMENT_DELAYED` alert it **clears** from the active view. Alerts are **deduplicated on status change** (an unchanged status across poll cycles produces zero new alerts; one status transition produces exactly one alert), and a `SHIPMENT_RECOVERED` event **clears the corresponding stale delay alert** from the active-alert list while retaining it in history. The surface is read/cross-link only — it never changes gate readiness, closes a finding, applies a mitigation, or alters a schedule date.
**Rationale:** PRD US-31 and the Agent Suite orchestrator paragraph now name the **full four-event contract** (`TEST_FAILED`, `SHIPMENT_DELAYED`, `SHIPMENT_RECOVERED`, `predicted_risk_delay`) that the Command Center must present, extending the three-event contract pinned in [[ADR-015]] with the Predictive Schedule Risk Engine's `predicted_risk_delay` producer ([[ADR-020]]). Status-change dedup and recovery-clearing are required verbatim by US-31 and the "100% correct alert deduplication" success metric, and reading only from the records the agents already write keeps the surface consistent with the append-only provenance graph (no parallel datastore). Presenting the Command Center as read/cross-link only is the frontend expression of the platform-wide AI-advisory-only boundary ([[ADR-006]]): the surface shows what fired and what it affected, but every consequential decision stays with humans and the deterministic engines.
**Trade-offs accepted:** The Command Center depends on the agents having already written their `schedule_events`/`findings`/`edges`/`audit_events` records, so an alert appears only after that write completes rather than at the instant a signal changes — accepted because the durable schedule/evidence pipeline is the source of truth, not a faster parallel alert store. Dedup and recovery-clearing logic must be exactly correct (a missed clear would latch a stale delay, a missed dedup would spam the surface) to meet the golden-set dedup metric; this correctness burden is accepted as the direct cost of a trustworthy single-pane alert view.

## Rejected Alternatives

- **Microservices (for the overall MVP, [[ADR-001]]):** rejected because independent deployment and cross-service authorization would add operational complexity before pilot scale requires it.
- **Long-running container API (for the overall MVP, [[ADR-001]]):** rejected because idle infrastructure cost conflicts with the free starting model.
- **Neo4j ([[ADR-002]]):** rejected because the MVP needs bounded typed traversals, not an independently operated graph database.
- **Managed/always-on cloud PostgreSQL ([[ADR-002]]):** rejected because it would add a paid always-on managed dependency; the pilot instead runs a **local** Postgres instance, keeping the same relational engine without the always-on cost profile.
- **Postgres large-object/BLOB columns ([[ADR-003]]):** rejected because large binary data would couple transactional storage to document volume.
- **Local filesystem ([[ADR-003]]):** rejected because a raw local filesystem does not provide durable, shared object storage with signed URLs and lifecycle management; a local object store (MinIO / filesystem-backed) provides those over the same local disk.
- **Vector-only retrieval ([[ADR-004]]):** rejected because exact identifiers and numeric clauses can be missed or distorted by embeddings.
- **FTS-only retrieval ([[ADR-004]]):** rejected because equivalent requirement wording would not be found reliably.
- **Synchronous request processing ([[ADR-005]]):** rejected because large files would timeout and a provider failure would make the upload outcome ambiguous.
- **LangGraph/CrewAI orchestration ([[ADR-005]]):** rejected because the workflow is typed, deterministic, and approval-gated rather than an open-ended autonomous agent loop.
- **LLM-generated readiness ([[ADR-006]]):** rejected because output is non-deterministic and difficult to audit as an approval basis.
- **Fully autonomous issue closure ([[ADR-006]]):** rejected because it would bypass engineering authority and evidence review.
- **Tenant-wide roles only ([[ADR-007]]):** rejected because contractors and consultants need access to selected projects, not the entire organization.
- **External enterprise SSO first ([[ADR-007]]):** deferred until a pilot buyer requires it; the authorization model will remain compatible with later SSO.
- **Native iOS/Android apps ([[ADR-008]]):** rejected because two additional codebases would slow the pilot and reduce deployment reach.
- **Online-only capture ([[ADR-008]]):** rejected because a failed connection could lose or misrepresent field evidence.
- **WASM OR-Tools build ([[ADR-009]]):** rejected because no official OR-Tools WASM build exists (an unofficial build would violate the Library-First Rule's intent), a WASM build would be forced single-threaded (a Node/WASM sandbox cannot spawn native OR-Tools threads) which degrades CP-SAT performance beyond toy DAGs, and in-process CPU-time/memory limits are a poor fit for solver runs whose duration is workload-dependent (TRD Tech Stack, Solver integration approach section).
- **Hosted third-party optimization API ([[ADR-009]]):** rejected because it would introduce an uncontrolled external dependency for a deterministic computation the product must be able to fully explain and audit (PRD constraint: "only the deterministic CP-SAT solver computes schedule dates, critical path, and feasibility"), and would complicate the tenant-isolation/no-shared-training data-handling requirements that a self-operated microservice can satisfy directly.
- **Calling the Gemini SDK directly from schedule services ([[ADR-010]]):** rejected because it would violate the existing "AI provider access goes only through `ModelProvider`" rule (CLAUDE.md Coding Rules) and couple schedule logic to one vendor.
- **Auto-accepting high-confidence extractions without review ([[ADR-010]]):** rejected because PRD success metrics require "100% of accepted schedule tasks and resource-capacity records with ambiguous/missing fields routed to human review, with zero silent auto-acceptance," and because human reviewers must remain in the loop per the Hard Constraints.
- **Letting the LLM propose dates directly / tune objective weights per project ([[ADR-011]]):** rejected because it would let a non-deterministic component influence computed schedule dates and critical path, directly violating the PRD's "only the deterministic CP-SAT solver computes schedule dates, critical path, and feasibility" constraint.
- **A single-objective (deadline-only) formulation ([[ADR-011]]):** rejected because PRD explicitly requires idle-time minimization as a secondary objective to "automatically pull forward independent tasks to fill freed slack."
- **Mutable in-place schedule updates ([[ADR-012]]):** rejected because overwriting the current schedule on every solve would make before/after audit reconstruction impossible and conflicts with the TRD's "Schedule version audit" NFR requiring full before/after reconstruction and hash-linking to the predecessor.
- **Re-solving on every event unconditionally ([[ADR-013]]):** rejected because it would generate unnecessary solver-microservice cost/latency for events with no schedule impact and would create version-history noise contrary to PRD's "without noisy churn" requirement.
- **Conforming the two agents to the platform's local Node/`ModelProvider` stack ([[ADR-014]]):** rejected per explicit user direction (StructuredPlan Divergence Note, PRD "Stack override" constraint) — the agents' Python/FastAPI stack stands as a distinct local stack for these agents rather than being conformed to the platform stack or left undecided; since the whole platform is local, there is no Cloudflare baseline to diverge from.
- **Running the agents' logic inside the local Node process ([[ADR-014]]):** rejected because their committed libraries (turfpy, PyMuPDF, ReportLab, `websockets`, Chroma, Neo4j/NetworkX) have no local Node-process equivalent; they are integrated as external Python services instead, the same pattern as the solver microservice.
- **Treating Chroma/Neo4j as authoritative platform stores ([[ADR-014]]):** rejected because Postgres + the `edges` table remain the single source of truth for provenance; the agents' Chroma/Neo4j are local working stores only, and their durable outputs are persisted through the local Node core.
- **Building the full durable orchestrator now ([[ADR-015]]):** rejected/deferred because the orchestrator's durable transport, routing rules, and replay/ordering are not-yet-settled; only the event contract the orchestrator must carry is pinned down at this stage.
- **A durable broker for the hackathon event bus ([[ADR-015]]):** deferred because an in-process `asyncio` bus is sufficient for the localhost-only demo; durable delivery into the schedule pipeline is already provided by posting through the local Node core `schedule/events` endpoint (backed by BullMQ/Redis).
- **Emitting an event on every poll cycle ([[ADR-015]]):** rejected because the ~30s AIS poll would spam the schedule pipeline; events fire only on a genuine status change, deduplicated against the last-notified status (PRD US-23).
- **Showing agent verdicts/reports as accepted rather than "Proposed"/"DRAFT" ([[ADR-016]]):** rejected because it would risk the platform-wide false-assurance failure mode — a completed all-pass test must set the gate to `PENDING_REVIEW`, never `READY`, with only an authorized approver transitioning a gate.
- **Linking test evidence before engineer approval ([[ADR-016]]):** rejected because PRD US-17/US-18 require export and evidence linkage only after explicit engineer approval of the draft report.
- **Naive straight-line polyline routes / ignoring the antimeridian ([[ADR-017]]):** rejected because a great-circle route crossing ±180° would render as a visibly wrong straight line across the map; routes are split at the antimeridian into continuous segments.
- **Presenting a great-circle-interpolated position as a live AIS fix ([[ADR-017]]):** rejected because PRD US-19 requires every position be transparently labelled live vs. simulated.
- **Letting the LLM judge numeric/boolean acceptance or produce the ETA/status ([[ADR-018]]):** rejected because PRD US-15/US-20/US-21 and the Constraints require these verdicts and values to be deterministic threshold math with zero LLM involvement; the LLM is confined to drafting and human-reviewed narrative suggestion only.
- **Auto-determining narrative/qualitative acceptance steps ([[ADR-018]]):** rejected because qualitative criteria are always routed to `needs_human_review`; an LLM narrative comparison may surface a "possible mismatch" as a suggestion only, never as an auto-verdict.
- **Trusting LLM-generated clause citations without verification ([[ADR-018]]):** rejected because every clause citation is verified against ingested-corpus metadata post-generation and hallucinated clause IDs are flagged, never shown as verified.
- **Auto-flagging narrative/qualitative compliance comparisons ([[ADR-019]]):** rejected because PRD US-24 routes every narrative comparison to mandatory human review as an "AI suggestion — possible mismatch," never an auto-flag; the review-queue UI tags them distinctly and requires human acceptance.
- **Showing an equivalence/substitution claim as a flag without visible grounding ([[ADR-019]]):** rejected because PRD US-25 requires equivalence claims to be grounded in a cited standards clause or approved-equal precedent, or downgraded to "needs engineering judgment"; the UI renders the grounding provenance (or its absence) inline rather than presenting an ungrounded claim as a flag.
- **Silently resolving a client-spec-vs-standard conflict in the UI ([[ADR-019]]):** rejected because PRD US-25 requires both sources be surfaced with document hierarchy/date; the flag panel shows a two-source view instead of choosing one.
- **A live socket stream / one-click "apply mitigation" for the risk surface ([[ADR-020]]):** rejected because the Predictive Schedule Risk Engine is a single periodic-poll agent whose mitigation options are advisory proposals only — the UI presents a poll-driven feed and hands a selected option to a human or the deterministic CP-SAT solver, never rescheduling from the surface (PRD US-26/US-27).
- **Fabricating or hiding a missing signal on the Live Events feed ([[ADR-020]]):** rejected because a missing signal feed must show an explicit data-unavailable state, never a fabricated risk or a silently dropped signal (PRD Edge Cases).
- **A general chatbot answering without source-region citations / a global (unfiltered) semantic search ([[ADR-021]]):** rejected because PRD US-28 and the Constraints require every claim to cite `source_region_id`/`document_version`/content hash and a mandatory-first deterministic metadata filter before any scoped vector search; uncitable claims are dropped and a no-results state is shown instead of a hallucinated answer.
- **A parallel graph datastore for the project graph/timeline page ([[ADR-021]]):** rejected because PRD US-30 requires the page read live from the existing append-only, hash-chained `edges` + `audit_events` tables via API with no parallel datastore.
- **Cross-project similar-RFI retrieval / auto-answering from a suggestion ([[ADR-021]]):** rejected because RFI similarity is project-scoped and suggestions are advisory only, never auto-answering or closing the current query (PRD US-29).
- **A three-event-only Command Center that omits `predicted_risk_delay` ([[ADR-022]]):** rejected because PRD US-31 and the Agent Suite orchestrator paragraph now require the full four-event contract; the Predictive Schedule Risk Engine's `predicted_risk_delay` must cross-link to its affected task(s) and mitigation options on the same surface.
- **Leaving a recovered shipment's delay alert latched / de-duplicating per poll instead of per status change ([[ADR-022]]):** rejected because US-31 requires a `SHIPMENT_RECOVERED` event to clear the stale delay alert from the active view (retained in history) and requires exactly one alert per status transition with zero alerts for an unchanged status across poll cycles.
- **A Command Center that mutates state (changes readiness, closes findings, applies mitigations, alters dates) ([[ADR-022]]):** rejected because US-31 makes it a read/cross-link surface only, consistent with the platform-wide AI-advisory-only boundary.
